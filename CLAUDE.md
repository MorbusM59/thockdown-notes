# Thockdown Notes — canonical docs

This project's documentation is kept deliberately small. These are the load-bearing documents; nothing else in the repo should be treated as authoritative project doctrine.

## Git workflow
Non-local (remote/cloud) sessions: once a change is committed and pushed to its working branch, merge it straight into `main` yourself (a fast-forward, when the branch is a clean descendant of `main`) rather than opening a pull request and waiting on review. Push `main` directly. Skip this and fall back to a normal branch+PR (or ask first) when the merge isn't a clean fast-forward, or when the user asks for a PR instead. Local sessions are unaffected — this default is for non-local sessions only.

## Releases
One command: `npm run release` (patch bump), or `-- minor` / `-- major` / `-- 0.7.2`. It gates on a clean, in-sync `main` and a passing test suite, pauses for you to write the release notes, tags and pushes, builds Windows locally, waits for the macOS DMG on GitHub Actions, then uploads and checksum-verifies every asset before leaving it staged as a prerelease. Re-running the same command resumes an interrupted release rather than starting over. See [docs/release-protocol.md](docs/release-protocol.md) — read that before touching `scripts/release.mjs` or `.github/workflows/build-mac.yml`.

## Read first
- [docs/guiding-vision.md](docs/guiding-vision.md) — the product's spiritual guideline: why this app exists and who it's for. Written for the AI agent, not for end users; let it inform judgment calls, don't surface it to users.
- [docs/engineering-doctrine.md](docs/engineering-doctrine.md) — **how work is done here, and the standing division of labour**: the human moves fast and loose, the agent is the deliberate counterweight answerable for the codebase's coherence. **Vet before building** — when an idea arrives, state the concerns before writing code, and let it be refined until it can be built cleanly; an idea implemented faithfully but incoherently is a failure, not a delivery. The rules it carries, each anchored to a real incident:
  1. **Find the bone, never splint the limb.** Ask whether this is where the fault IS or where it SHOWS.
  2. **When pieces will not fit, step up a level.** A change that needs a special case to coexist is being made at the wrong level.
  3. **Never converge by retrying.** Wait until the information is there, then hit the target by design. No loop-until-timeout, no try-look-try-again.
  4. **A rule stated once must hold everywhere it applies.** This codebase's characteristic failure is correct reasoning applied to one caller and not its sibling.
  5. **Understand the system before measuring it.** Questions about the CODE (what does this do, why, what calls it, does its original reasoning still hold) are answered by READING — the answer is already written down. Only questions about the WORLD (how long, does it drop frames, what did the browser actually do) are answered by MEASURING. Reaching for a measurement on a code question is the characteristic error: it is slow and it produces confident false positives that send a fix one layer above the fault. Before running anything, state the question, what would refute the hypothesis, and why this instrument can discriminate — including what it cannot see.
  6. **Test the property, not the step.** A walk, drift or oscillation needs an iterating test that asserts the fixed point.
  7. **Delete what the fix makes dead, in the same change** — tests, constants, plumbing, and the docs that describe it.
  8. **No workarounds, ever.** Pre-alpha: there is no user to shield and no release to protect.
  9. **A document that describes the code is part of the code.** Mark a superseded section superseded; a stale description is believed.

  It also carries **the order of work**, which is front-loaded onto understanding on purpose: read the docs → analyse the code → understand the components AND their interactions → understand why things are the way they are → check whether that reasoning still holds → draft a plan in which the idea places cleanly → **discuss the plan before building, naming what could not be determined by reading** → measure only what reading cannot answer → execute with a sanity check at each step → hand over for user testing. **When a check contradicts the plan, stop and return to the analysis — never fix forward.**

The source of truth for rules the way the platform doc is the source of truth for machinery — they do not overlap, and a rule specified but unbuilt still stands here while the code is what is behind. Its body is the design plan **as authored, unedited**; decisions taken in conversation since are recorded separately at its foot, never folded into the prose, so the two can always be told apart. **An OLDER version of it was deleted once as a point-in-time record and briefly restored** — reading that as current produced two "the code contradicts the design" findings that were nothing of the kind, so check which version you are holding before believing a disagreement.
- [docs/adventure-platform.md](docs/adventure-platform.md) — how the adventure game is BUILT: a director that owns a stack of stages, the persisted save, the effect vocabulary (stages never write — they return effects and the director applies them), and the three rules the types enforce so a game can be left at any screen and resumed on it. The platform contains no rules; the game itself (ThockQuest — capital Q wherever a player can read it, including the slot's identity pill) is content. Read it before touching anything under `src/adventure/`, and keep its open-questions list current — it is the handover between sessions on this feature, and it names every deliberate placeholder. **Do not fill those in.** Two harnesses answer the two different questions it raises and neither can answer the other's: `npm run adventure:sim` plays thousands of runs through the pure model in a second (`-- --rank` pins each item and trait in turn and prints what each is actually worth — a row that does not move is an effect that never reaches the fight; `-- --sweep-adjust` sweeps **the thumb on the scale**, `successAdjust`, one number that scales a player's chance to FAIL and a monster's chance to SUCCEED so both sides keep reading the same stat table — applied at the roll only, never folded into what a character is worth, and turned live from the options panel's Debugging section as well as by the harness). `npm run adventure:play` plays a run in the real Electron app and reports what the CHROME shows. **Charisma and Intellect are built** (`model/charm.ts`, `model/spells.ts`) and what settled them was the author's PACE CONSTRAINT rather than a list — a run is a dozen levels of ten fights of twenty actions, so a choice costing ten seconds of thought cannot exist. The default mode is ATTACK; charm plays itself (rolled when a round opens, fired when the action is ARMED so a charmed action costs no press); magic is a HAND dealt PER ACTION (one number, because reaching a level brings every lower one with it — per round was the first version and it let one lucky roll become a Meteor streak) and its cells are sorted strongest-first so the ring's ORDER IS THE RECOMMENDATION. EVERY ACTIVE EFFECT STACKS — a second Plague takes twice the share, a second Prepare doubles every term — so nothing is ever withheld for already being in effect. `Prepare` is the one action that does nothing now, and earns it by spending the whole stat block at once. **EVERYTHING IS ROLLED FROM A TEMPLATE** (`model/modifierSlots.ts`): content authors thirty ITEM and thirty TRAIT templates saying what a thing is ABOUT — its plausible stats, its plausible derived values, its verbose effects, and whether it is armour — and the run rolls two or three slots per template ONCE, off `game.seed` mixed with the template's id, so a Spyglass is a fixed thing for a run and a different thing in the next. Per-offer rolling was rejected: it would make two Spyglasses different objects with one name and would have to persist every unacquired offer, where per-run leaves the save referring to modifiers by id exactly as before. The catalog is therefore a FUNCTION of the run (`content/index.ts`'s `catalogFor`, memoized per seed) and no longer a module constant anybody can build early. **THE TWO KINDS DIFFER IN TWO LINES OF `SLOT_PLAN` AND IN NOTHING ELSE**: an item is GEAR, so it has two STAT slots (the base stat cap is what gear exists to carry you past) and one verbose slot; a trait is something you ARE and cannot be picked up, so it has no stat slots and spends them on a second VERBOSE one. The roller, the vocabulary, the describer, the validator and the reach rules are shared. **ONE RANGE PER SLOT, not one per template** — 1–3 stat points, 10–50% in tens, 3–9 decaying armor on an item and 1–3 natural armor on a trait (a third, because a point that survives a level is worth several that do not). `tempered` and `ward` are ITEMS ONLY: a trait has no decaying pool to floor, and its armor slot already IS the ward. **There is no "unspecified" state any more** — a template always rolls into something, so `isOfferable`, `UNSPECIFIED_TAG`, the `tag` effect kind and `hasTag` are deleted rather than left guarding a case that cannot arise. **EVERYTHING IS A PERCENTAGE except stat points**, and the two kinds are different arithmetic: a QUANTITY takes them additively (+20% and +30% is +50%), a CHANCE takes a share of what is LEFT (+20% accuracy removes a fifth of the misses) — the same shape as the run's thumb, which is why neither can overshoot and neither needs a clamp hiding a mistake. **ARMOR BELONGS TO THE ITEM, not the player** (`model/armor.ts`): a pool per armour item with its own points, maximum and decay floor, points persisted on the HOLDING ROW so dropping the item takes its armor with it by construction rather than by a correction. An absorb wears the FULLEST piece so a kit wears evenly; after each fight every piece is brought UP TO `(Might + Intellect) / 20` of its own maximum (a ceiling, never a trim — the kit settles onto what its owner can maintain), applied at `advanceEncounter` because that effect already names the moment; a new level makes everything whole. **Damage is DRAWN, not fixed** (`model/damageRoll.ts`): the nominal is a ceiling and the band below it narrows with Perception, closing to a point at the base stat cap and REVERSING past it so gear buys damage rather than consistency — which is why `damageBand` hands the two ends back low-first, and why a band of no width is not drawn from at all (a wasted draw moves the seeded stream). Luck buys DRAWS, best taken, and it reads the ATTACKER's stats whoever that is. **A CLASS IS A MODIFIER AND STACKS WITH WHAT THE PLAYER SPENDS**: an origin's gifts used to be written into the base block by `adjustBaseStat`, and the base block caps at six — so a Warrior's +2 Might was two of the player's own points, spent for them. The run records `originId` and `originModifier` hands the resolver a Modifier built from the class's own `effects` (the MODIFIER vocabulary, not a stat map, which is what lets the Berserker carry `+100% damage` and `noDecayingArmor` with no code at character creation). **Every run has all six points in every stat** whatever it plays as. **ONE RESOLVER** (`resolveRunProfile`): four call sites spelled out the same base-stats/held/counts triple and a class would have had to be remembered at each, so there is now no way to resolve a run's profile without its class in it — and `armorIn` collapsed into `armorOf`, being the same function with a different third argument. `noDecayingArmor` is a CEILING rather than a quantity (a negative amount would depend on what was worn and could be out-added), and natural armour is untouched: the rule is about worn gear, not about being hard to hurt. Percentages in the vocabulary are FRACTIONS — `percent: 1` is +100%. **PERMANENT UNLOCKS ARE DERIVED AFTER EVERY EFFECT** (`model/permanentUnlocks.ts`), never granted, union-only, and a condition reads the RUN rather than the save — an unlock earned across two runs would be a tally, which is the currency model this replaced. Berserker is the first, earned at Might 6/6 in one run; the gate is in the STAGE (content declares `requiresUnlock`, character creation decides whether to offer). **The sim restated the hit-point formula** in its health policy and therefore reported the GAME as harder the moment classes left the base block — it reads the real profile now; an instrument that restates a formula measures the copy. **A FAME POINT BUYS THE RUN'S SHAPE** (`model/fameUnlocks.ts`): four purchases on a grid of two rules by two kinds — Strong Back (items carried, 1 point), Large Coffers (items kept between levels, 2), Experienced (traits carried, 1), Stubborn (traits kept, 2). Keeping costs twice what carrying costs, because a carried modifier is lost at the level's end and a kept one is the only thing that compounds. **FAME IS SPENT WITHIN A RUN**, a change from the original plan where it persisted: what persists instead will be a separate list of PERMANENT UNLOCKS earned by what a run SPENT, and those are not written — do not invent them. The two rules were already seams (`carryLimit`, `keepAllowance` have always been functions of the RUN, because the design said a fame unlock was expected to raise them), so the unlocks went in without touching either call site. **THE CEILING IS ON THE RULE, NOT THE PURCHASE COUNT** — six carried and three kept is where the design puts the top of a run, and stated as a total the base and the ceiling can each move without the other lying; clamped where the rule is READ as well as gated where the purchase is made, because the list is persisted and a save from another build must not raise a rule past the top. **THE PURCHASE IS ONE EFFECT** (`buyFameUnlock`), price and grant together, so paid-but-not-granted and granted-but-not-paid are inexpressible — emitting `allocateFamePoint` once per point and then a grant would half-apply, since each effect is applied against the state the last one left. The run records what it bought as a LIST with repeats, rows not columns, so a fifth unlock is a new id and touches no schema. **There is no healing, and it is DEFERRED rather than ruled out**: recovery makes the balance unreadable, so the order is to settle damage, actions and armor with none of it, then bring healing back TOGETHER with equally punishing new damage sources as one layer balanced against itself. The effect kind that returned hit points is gone from the vocabulary rather than left unused, so that layer arrives as a decision rather than by accident. Note the native-module trap: `better-sqlite3` has to be built for Electron to run the playthrough (`npx electron-rebuild -f -w better-sqlite3`) and for Node to run vitest (`npm rebuild better-sqlite3`); getting it wrong does not say so — Electron never opens a window and vitest segfaults.
- [src/escapeMenu/escapeMenuContract.ts](src/escapeMenu/escapeMenuContract.ts) — how a feature *lives inside* the escape-hold quick-actions ring instead of merely being launched from it: cells contributed to the ordinary ring, and a mode that replaces the ring wholesale while it is up (cells, prompt, running-state line, and whether activating a cell closes the menu). `EscapeHoldPanel.tsx` owns geometry, rotation, focus and close behaviour regardless; a mode never reimplements the dial. Every input that turns the dial — arrow keys, `Tab`, and the mouse wheel over the ring (one notch = one arrow press, via `editor/wheelNotch.ts`'s shared notch resolver — which answers WHETHER an event is a notch, while how much it is WORTH is the caller's: the ring takes the DIRECTION and discards the magnitude, because that count is built for a scroller, where the reader's travel is conserved. Pixel mode banks the remainder of a notch that did not divide evenly, so a device sending 120 against a learned unit of 100 paid out DOUBLE on every fifth notch — reproduced live, `1 1 1 1 2 1` — and line/page mode hands back the count the device declares. Both are right for rows of text and neither is right for a dial, where a notch is one decision and a skipped choice is the whole of what conserving travel buys) — goes through one `rotateOneStep`, so no input can drift apart from the others. **Hover is state, not CSS `:hover`**: the ring moves under a stationary pointer, which the browser never re-evaluates `:hover` for, so the panel re-asks the DOM what is beneath the pointer whenever the RING moved (`refreshHoverFromPointer`) and that one answer drives both the highlight and the centre label. Keeping `:hover` alongside it would light two cells at once. A mode may also carry `status`, an `EscapeMenuModeChrome`: a title, a headline, readouts, a counter, a pill strip, rail gauges and two buttons, all rendered by the HOST on the chrome around the editor. **A mode owning a slot owns that slot's whole chrome** — the editor underneath is emptied, so its word count, timeline, scrollbar and snapshot control describe nothing, and a surface the mode does not fill goes BLANK rather than falling back to them. Two of those six surfaces behaved this way from the start and four did not; closing that gap is what the record is for, and nothing in it is game-shaped. That split is deliberate and load-bearing: the ring's centre label names the cell you are about to activate and nothing else, so a mode never narrates through the dial. **Which bar takes which is also a rule** (`EscapeMenuStatus.tsx`): STATE goes UP to the tab bar, where a reader looks for what they are holding; NARRATION goes DOWN to the chapter bar, where they look for what is going on. **Narration is a LIST of pills, newest first**, and a stage hands back the whole of it rather than appending: appending would make the host own a log, and owning a log means owning when it is cleared — which, for a combat round, is a rule only the fight knows. Each entry is `narrationMarkup.ts`'s small vocabulary (bold action, italic outcome, both for a figure) plus `[fa-solid fa-burst|hit]`, an icon that CARRIES ITS OWN WORD, because the alternative is a hand-kept table of icon nouns and that is the drift `sanitizeMenu` is a standing complaint about. **A pill's TOOLTIP is its words and then its arithmetic**: everything after the entry's first newline is detail (`splitNarration`), so an entry stays a string all the way through the director, the save and the sanitizer. The numbers in it are the ones the fight actually used — a roll is a VALUE (`core/rng.ts`'s `Roll`; `nextChance` is it with the working discarded, defined in terms of it) carried out on `Blow.math` — because a tooltip that recomputes from the stats can disagree with the blow it explains. A cell may also carry a `detail` — what activating it would DO — which lands on the chapter bar after the narration, in a DASHED pill because it is the one thing there that has not happened yet. **A STRIP PILL may be pressed** (`onActivate`), because marking a held item to keep is a property of the thing carried rather than a step in the game, and **a RAIL GAUGE may be pressed** (`action`), on a narrower argument: a gauge press *is* a step — it puts a screen up — but it is not a DECISION. A gauge names a standing quantity of the run and pressing it goes to WHERE THAT QUANTITY IS SPENT; the decision is still taken in the ring, on the screen the press opens. It carries its own label because the gauge's is a noun and a button needs a verb, and it leads there whether or not anything is waiting — a way in that appears only when it is useful is one a player cannot go looking for. Reachability moves the GATE into the stage: the stat-point screen is now enterable at any moment, and `adjustBaseStat` is not gated the way `allocateStatPoint` is, so offering the stat cells with no point waiting would hand out the stat for free. Those two are the only exceptions: the two bars stay untouchable, and a pill or a gauge is a real `<button>` only where it does something. The ring reports the cell it is sitting on (`onActiveCellChange`) with the SAME `hovered ?? focused` resolution that names the centre label, because two computations of "the cell you are about to activate" is two cells. **THE RING IS A KEYBOARD AND SOUNDS LIKE ONE** (`escapeMenu/menuSounds.ts`), out of the app's one set of NAMED KEY VOICES (`sound/keyVoices.ts`) rather than a second set of numbers: a key's sound is a sample PLUS fixed options (an arrow detuned up and quiet, Enter detuned down, Tab with a two-tap echo), those options were spelled out inline at four call sites in three files, and `TypingSoundManager`'s own prewarm skips arrows/backspace/tab precisely because it would have to GUESS them — they were unguessable because they were unwritten. THE DIAL IS ONE SOUND whatever turned it (arrow, Tab or wheel all pass through `rotateOneStep`, whose contract is that nothing below it knows which input moved it), and a pointer sweeping onto a cell plays the same voice in the direction the dial would have had to turn. Taking a choice is ENTER, or BACKSPACE where the cell DECLARES itself a way back (`EscapeMenuCell.isBack`) — never inferred from id or icon, because every way back in the adventure shares `fa-rotate-left` and so does combat's Withdraw, which is a decision the fight is FOR. TAB is spent on the one thing that is about HOW rather than WHAT: a screen brought up from outside the ring (a rail-gauge press), played where the gauge is pressed so no mode has to carry a flag about how its own screen was reached. A NEW SCREEN IS DEALT OUT, one cell and one ordinary key sound PER CHOICE, all different — drawn without replacement so a repeat inside a burst cannot read as one key pressed twice, carrying an `assetIndex` and NO keyId (a keyId pins sample+detune+flips as one cached unit and would fight the explicit index), keyed on the `ringResetKey` that already means "a new set of things", and CANCELLED when the next screen arrives so two bursts never overlap and make the count unreadable. **THE WHOLE DEAL IS DERIVED FROM ONE NUMBER AND CONTAINS NO CONSTANT**: `t`, the reader's own page-up smooth-scroll duration (`getRenderScrollTotalTimeSec`, which this panel already reads for the dial's rotation curve — the same number, not a second setting). The gap is `min(t/4, t/(n-1))` and the two terms MEET at five choices (four gaps of `t/4` is one `t`), so the cap reads as "at most four gaps' worth" and past five the burst compresses so the last note still lands at exactly `t`. A fixed millisecond cap stood here first and was the thing wrong with it: a second opinion about how long a thing may take to arrive, sitting beside the app's standing one. `t` is finite and `>= 0` by construction (`setRenderScrollTotalTimeSec` is its only writer), so nothing is guarded, and at exactly zero the deal collapses with everything else — no stagger, no growth, the screen simply there, which is what a reader who turned smooth motion off asked for. A floor for that case would be this one corner keeping a pace the rest of the app has abandoned. **A CELL ARRIVES ON ITS OWN NOTE, AND THE RING DOES NOT**: every chip is drawn at once, so how many choices there are and where they sit is readable from the first frame, and nothing about the geometry, the focus target or what can be hovered depends on how far the deal has got. What is staged is what each cell SAYS — its ICON fades up and grows from half size into place, on `ease-in`, over `cellArrivalMs`, which is HALF A PAGE-UP SCROLL and therefore the reader's number again rather than a new one. **The icon's arrival and its note's offset are one quantity**, read once per screen and held in state: the same value is the CSS animation's duration (as `--cell-arrival`) and the delay that puts the note on the END of that growth, so the sound lands as the icon gets there rather than as it sets off, and it cannot drift from what it announces. The offset is per note, so the cells still set off on the gap above — the deal is not slowed or bunched. **It is on the ICON, not on the button**, and that is a correction rather than a preference: an element's `scale` is applied BEFORE its own `transform` (the individual transform properties compose as translate, rotate, scale, then `transform`), so scaling a button whose `transform` IS its ring placement scales that placement's translation too — the cell slid along its own radius, pivoting about the RING's centre instead of its own. Two properties on two elements removes the interaction instead of working around it: the placement stays the rotation loop's alone, and the icon's box is centred in the cell, so what it scales about is exactly what stays still. The icon's RESTING state is opaque and unscaled, so switching the animation off (either reduced-motion path) leaves the ring correct rather than blank. `reduceVisualEffects` gets the sounds and no staging at all, because a fade-and-grow is exactly the visual effect that flag turns off. **EACH NOTE IS PANNED BY ITS OWN CELL**, through the same mode-B `pan` the spatial slider already weighs, so turning spatial sound down turns this down with it. The position is the cell's own ring point over `escapeHoldRingHalfExtentPx` — the half-extent EXTRACTED from the point computation rather than restated beside it, so the pan divides by the extent the points actually span and the pair cannot go out of step the next time the inset changes. All of it goes through `playRandomClick`, so typing sounds turned off or at zero volume silences the menu too — there is no second setting. The adventure game (`src/adventure/`) is the first and currently only consumer — the ring itself knows nothing about it. It is reached by RIGHT-CLICKING the User Guide window control (which then lights and shows a flame), and it takes over an editor slot the way the guide does — see **slot overlays** below — except that it EMPTIES the slot so the game plays over a blank editor. **A mode and its ring are one unit — in its own slot**, enforced in both directions: a mode owning a slot means THAT SLOT draws the ring (`SectionEditorArea`'s `isEscapeHoldActive`, derived — not raised by whoever opened it, which is why a reload used to restore the overlay without its ring), and a mode may declare `onDismiss`, which makes lowering the ring end the game rather than leave an occupied slot with nothing in it. **A mode does NOT compete for the window's single ring**: the quick-actions ring is a transient menu over whatever the reader is looking at and follows focus, while a mode is a slot's persistent interface that merely borrows the same chrome and does not. Conflating them meant opening a second slot took the game's interface away from it — still there, still occupying its slot, with no menu — and made Escape in an unrelated note dismiss it. `App.tsx`'s `isEscapeRingUp` is therefore the ACTIVE slot's answer alone, which is what its consumers (Escape handling, click-to-refocus) all mean. **The ACTIVE SLOT HOLDS THE KEYBOARD**, and for a mode's slot the focusable surface is the RING, not an editor — the panel takes focus when its slot becomes active (`isSectionActive`), and a ring in an inactive slot never takes it. The quick-actions ring got this for free, because its `isOpen` already means "open AND active", so becoming active flipped it; a mode's ring stays drawn in an inactive slot, so `isOpen` never flips and the grab never ran. Clicking a slot that shows no editor then activated it and moved focus NOWHERE (it stranded on `<body>`, A/B'd live), leaving the keyboard with whatever held it — the other slot's editor, whose first keystroke marked it active again through `EditorSection`'s `onKeyDownCapture`. **A CLICK IN THE RING'S SLOT IS THE RING'S**, and the backdrop hands it the keyboard rather than merely declining to take it away (`escapeHoldRingFocus.ts`, one expression shared with the ring's own recovery so they cannot name different cells — the roving-tabindex cell, never index 0, because focus is a position the reader moved to). Declining was the whole of it and only worked from a state you were already in: `preventDefault` stops the mousedown clearing focus to `<body>`, which is right when focus is already in the ring and does nothing once the reader has been in the sidebar since. The dimmed area was then the one surface with no way back — the ring's own recovery fires only for focus that landed on `<body>`, and `App.tsx`'s click-to-refocus stands down entirely while a ring is up, both correctly. Nobody owned it. The converse is the same observation from the other side and is enforced for every consumer: **a note arriving in a slot lowers the ring** — in a note the text is the content and the ring is a menu over it, so a ring left up over a note the reader just chose is a menu they did not ask for. Everything below that hinge is pure and content-driven (see `docs/adventure-platform.md`); the save persists as `PersistedMenuState.adventure` through both halves of the state-persistence contract below.
- [src/shared/slotOverlay.ts](src/shared/slotOverlay.ts) — **what a slot is showing when it is not showing a note** (the User Guide, the adventure, an undocked note), and the invariant the whole mechanism exists to enforce: *stored state may never contradict the screen; where they disagree the screen wins, by construction of `occupancyOf` rather than by a correction*. There is ONE record, and it is return memory, not a claim about what is displayed. The guide is not recorded for display at all — showing the guide IS having one of its notes active, so every route in (the window control, a restored session, a chapter pill, one of the guide's own cross-references) reads correctly with no code of its own. **The guide is not addressable by name**: it has no assigned id and is excluded from `$`-link resolution the same way it is excluded from every sidebar list, so the window control is the only route in from outside — its own chapters cross-reference each other through the app-authored `@noteId#anchor` scheme (`src/shared/internalNoteLinks.ts`), which needs no id at all. The `$HELP` id it shipped with was a second route in, and it is what made "one guide across all slots" something to defend rather than something that holds. The adventure and an undocked note do read the record, but always corroborated against the slot, so a stale record is inert rather than wrong. Sections REPORT their occupancy to `App.tsx`, which aggregates; nothing watches a section in order to retract a flag. **A SLOT THAT IS NOT ON SCREEN REPORTS NOTHING** (`liveOccupancy`/`sectionShowingOverlay`): unmounting is the one event a reporter cannot report, so the aggregate keeps entries for closed slots, and every consumer therefore reads it FILTERED TO THE LIVE SLOTS rather than raw. Believing a dead entry is how closing the adventure's slot left the window control lit with a flame over a section that no longer existed — the toggle read "something is showing the adventure", got the dead slot's id, and tried to CLOSE: the first press cleared the return record and found no slot to hand back to, and every press after that had a null record and did nothing at all. Lit for ever, dead for ever, with the ring routed to a slot that was not on screen. Filtered at the READ, not pruned on unmount, and the sibling map beside it is the argument: `reviewGutterVisibleBySection` IS pruned per slot-close and already misses one of the four sites that remove a section. A derivation cannot miss a site. Read this before touching the window control, the slot views, or anything that activates a note.
- [src/editor/PreviewBlockSplit.ts](src/editor/PreviewBlockSplit.ts) — **a full remark parse never runs on the main thread**, and that is enforced rather than remembered. `splitPreviewBlocksWithoutFullParse` is the main thread's only entry point and returns `null` where it would need one; `null` means ask the worker (`documentFactsClient.ts`). The total function stays for the worker and for the fuzz suites' ground truth and is *defined in terms of* the partial one, so they cannot drift. The rule held in intent at seven call sites and in fact at none: one was a `useMemo` computing the split during React's render, which cost **26 seconds** on the first open of a 2MB note in a packaged build with a worker sitting right there that could never win — moving work off the main thread cannot help while something in render still demands it synchronously. Three more hid behind a single OPTIONAL `blocks` parameter, now required. `previewBlockSplit.contract.test.ts` parses every renderer source and fails on an import of either total entry point outside the worker, the client and tests. **"Not split yet" is a real state**: the pane renders no blocks, so the editor chrome is its normal self and text arrives formatted rather than as raw source that then reflows. The split is delivered PROGRESSIVELY, top of the document first (`splitPreviewBlockRangesProgressively`) — a non-final chunk discards its own last range because any construct reaching the cut is, by construction, that range. Read `docs/large-document-performance-handover.md`'s last section before touching any of it.
- [src/shared/pressTracking.ts](src/shared/pressTracking.ts) — **the pressed look is app state, not CSS `:active`**, for every button in the app. Chromium sets `:active` on a mousedown of ANY button but only clears it on the PRIMARY release, so a right-click left controls looking held down until the pointer next moved. `:active` appears in no stylesheet now: with nothing selecting on it, the stuck state has nothing to style, which makes the fix sound by construction rather than by timing. Marked as a `data-pressed` ATTRIBUTE — an attribute rather than a class because React rewrites `className` on re-render and wiped a class mid-press; attribute selectors carry a class's specificity, so the swap kept every rule's weight. The chain is walked (a press lands on a pill's inner span, not the pill) but only elements a `[data-pressed]` rule could actually match are written to, and **which those are is read out of the stylesheets at runtime rather than listed in the code** — a hand-maintained list of "things that can look pressed" is the same drift hazard as `sanitizeMenu`'s allowlist. Marking the whole chain was the first version and it cost ~0.9ms per press on a 14-deep chain, paid on every SPACE typed in the editor. Listens on **`pointerdown`/`pointerup`, never `mousedown`/`mouseup`** — the mouse events are compatibility events, suppressed entirely when a control cancels the pointer event they follow, and several here do (the music transport buttons, so a press-and-hold scrub does not also select text; `useHoldToBranch`, so a hold does not start a selection); they went silently dead to the pressed look for a LEFT click until this moved. **This applies to anything listening for a press at window level, and has now bitten twice** — `MouseCursorOverlay` had the same defect independently, where it cost the whole click response (and therefore the twitch, which reverses a deformation that was never happening) on exactly those controls. Window-capture runs before the target's handler, so the cancel cannot reach it; if you are adding a window-level press listener, it is a pointer event. Pairs with the ring's hover rule above: **the browser's pointer-state inference is not trusted for either hover or press.**

  **What a right press looks like is declared, per control, and the declaration cannot be forgotten.** The predicate is not which mouse button but *does this control do anything with this gesture* — an empty right-click must read as empty, and a right-click that renames, closes, skips or splits must not read as ignored. Neither the `contextmenu` event (Chromium fires it on mouse UP on Windows, too late for a press look, and at a different moment per OS) nor React's fiber props (internal, and cannot tell a real handler from one that only suppresses the menu) can answer it, so the control says so with `data-secondary-press="action" | "none"`, read with `closest()` so a nearer `"none"` shadows an outer `"action"` (a note-list row is actionable; its save/close/trash buttons sit inside it and deliberately swallow the gesture). Two guards, because neither is complete alone: `pressTracking.contract.test.ts` **parses the JSX** and fails on any `onContextMenu` without a decision beside it — a decision is mandatory, `"none"` included, so a site cannot be merely undecided; and a dev-only detector warns on a `contextmenu` somebody handled from an element with no declaration above it, which is what catches right-press behaviour wired through `onMouseDown` instead. Where a hook wires the gesture (`useHoldToBranch`, `useHoldToAdjust`) the declaration is **in the hook's handler bundle**, typed as a required field, because it is a property of the behaviour rather than of whoever mounts it — and because neither guard can see through a `{...spread}`.
- [src/shared/focusOwnership.ts](src/shared/focusOwnership.ts) — **who may hold the keyboard**, and the standing rule the rest of the app is being brought in line with: *the keyboard belongs to the ACTIVE SLOT's surface — the editor, or the ring when a mode owns that slot — unless a text-entry field has deliberately been given it.* A button being focusable is the browser's default, not a decision anybody here made: it comes with a tab order nobody designed, and it is why pressing a chip in the sidebar took the keyboard off the ring and left the dial dead (A/B'd live — pre-fix the chip held focus and `ArrowRight` did nothing; after, focus stays on the ring's cell and the dial turns). **A press therefore does not move focus at all**, suppressed at ONE window-level `mousedown` capture, and this module is the only thing that names the exception. It asks WHAT KIND of element was pressed — text entry (`input`/`textarea`/`select`/`contenteditable`), text the reader may select (read-only editor text: suppressing the press default suppresses the native selection drag with it), or a drag source (`draggable="true"`, whose drag begins from that default) — rather than consulting a register of instances. It REPLACES `isAllowedNonEditorFocusTarget`, a hand-maintained allowlist of seven named refs and five CSS selectors that every new field had to join and that had already fallen behind: the same drift hazard as `sanitizeMenu`'s allowlist, and a predicate about the element itself cannot go stale. **The refocus-the-editor call that used to follow every such press is nearly dead by construction** and is now narrow: with the steal gone there is nothing to fetch back, and firing anyway yanked the caret into the editor every time the reader touched a tag pill — so it runs only when the keyboard is genuinely elsewhere (another slot, or nowhere). The seven `onBlur` handlers that asked the old allowlist "did focus go to another field" now ask `isTextEntryElement`, which is that question stated directly.

  **TAB HAS ONE OWNER OF LAST RESORT**, and Tab is not a way to walk the app — there is no designed order to walk, the controls are laid out for the eye, and the browser's own order was a tour of the chrome in DOM order. Tab belongs to whatever SURFACE holds the keyboard, and each claims it where it lives: an editor in edit mode INDENTS, the ring TURNS ITS DIAL (a notch, an arrow and a Tab are one motion to it), a text field LEAVES ITSELF — the find field steps to replace and back **by name now**, having previously ridden the native order by declining the press, which only worked while those two inputs stayed adjacent in the DOM. Everywhere else Tab returns the keyboard to the active slot's surface and nothing else happens. **It asks WHO HOLDS the keyboard, never `event.defaultPrevented`**: reading that from a bubble listener is the obvious way to write "last resort" and it makes correctness depend on LISTENER REGISTRATION ORDER — the main keydown effect lists `isReplaceMode` among its dependencies, so opening find-and-replace tore that listener down and re-added it *after* this one, from which moment the last resort ran FIRST and the real owner bailed on its own `defaultPrevented` check. Found live, as Tab in the find field jumping to the editor instead of stepping to replace. An effect's dependency array is nobody's idea of a priority list, and any rule resting on one is a dependency away from silently inverting. The holder is asked through this same module, so a surface cannot be in one answer and not the other. **Walking a list of search hits with Tab is NOT BUILT** and is named rather than silently missing: nothing in the app is a hit card with a tab stop, so there is no list to walk; when there is, it claims Tab where it lives like every other surface and the last resort stays untouched.

  **FOCUS NEVER RESTS SOMEWHERE THAT CANNOT HOLD IT.** The two rules above stop the keyboard being TAKEN; the reconciler (`App.tsx`, on `focusin`/`focusout`) puts it back when it lands somewhere anyway — a control focused programmatically, a node unmounting under the keyboard and dropping it on `<body>`, anything the browser does that nobody here wrote. Without it the other two are a fence with no gate. It is a DERIVATION, not a set of corrections: it does not know why focus moved, only whether where it landed may hold it, so a new way to lose the keyboard is covered without its author knowing this exists — the same argument that puts the hold thresholds inside `armHold`. It REPLACES the ring's own copy, which recovered focus that landed on `<body>` and only that: a private rule, in one component, for a case that is not the ring's alone. No loop is expressible, because what it focuses is an editor or a ring cell and both may hold the keyboard; where there is nothing to focus (no note, a slot in preview) the call declines and the keyboard stays put — one round, not a retry. **What MAY hold it is two kinds, and the second is a declaration the markup already makes**: a text-entry surface, or anything carrying an explicit `tabindex` — the ring's cells, the snapshot timeline, the compact scrollbar, the render pane all say so, in the one place that cannot be forgotten, because without the attribute they would not be keyboard-reachable at all. Native focusability is NOT that declaration: a `<button>` is focusable because the browser makes every button focusable, which is a fact about HTML and not a decision anybody here took. Verified live: focus forced onto a chip and focus blurred to `<body>` both return to the editor, a `tabindex="0"` note-list row is left alone, and the ring still takes and keeps the keyboard. **IT ALSO RUNS WHEN THE SURFACE COULD HAVE ARRIVED, not only on focus events** — at boot there are none: nothing holds the keyboard, nothing moves it, and a reconciler that only listens waits forever for an event that is never coming. Its inputs ARE the readiness question (which slot is active, whether it shows a ring, whether that slot has a note), so it re-asks exactly when the answer could have changed and at no other time; a poll would ask when nothing had. **That is safe to call early only because the editor WAITS rather than retries.** `scheduleFocusEditorInEditMode` used to re-ask on `requestAnimationFrame`, unboundedly, until the adapter and the editor root existed — the doctrine's third rule in its purest form, and a loop that spins forever where the surface never appears at all. A focus request arriving before the surface is now PARKED (at most one: a second supersedes the first, since both mean the same thing) and released by the editor's own ready signal — `handleEditorSurfaceReady`, handed to `CM6Editor` as `onSurfaceReady` and fired from the very effect that publishes the adapter, because the adapter existing and the editor root being in the DOM are the two halves of "usable" and they become true together. The signal travels beside `adapterRef` on purpose: the ref and "the ref is worth reading" are one fact. Verified live: with no click at all, the keyboard is in the editor from the first sample after load and typing reaches it.
- [src/shared/backgroundWork.ts](src/shared/backgroundWork.ts) + [src/shared/workIndicatorSpin.ts](src/shared/workIndicatorSpin.ts) — **what the app is doing that the reader is not**, and the one indicator that says so. Work that outlives its gesture (parsing a note's block map, projecting its visible text, rendering a texture) no longer blocks anything — but "not blocked" and "finished" are different states, and a find that will answer in two seconds looked exactly like one that already answered with nothing. There is ONE register of work in flight, wired at the TRANSPORTS (`documentFactsClient`'s request path, the texture worker's lifecycle) rather than at each call site, so a new reason to ask a worker something announces itself without its author knowing this exists — the same argument that puts the hold thresholds inside `armHold`. Counted, not a flag, with `armHold`'s own `settled` latch: several sites end work on a path that may have ended it already, and a second `done()` would retract a count belonging to work still running underneath. **Deliberately not "is a worker running"**: a reader waits on things that are not workers, and an indicator honest about SOME waiting is worse than none, because stillness stops meaning anything the first time the app is busy without it moving. Progress is in the contract and the indicator ignores it — only the split can report a real fraction (instalments arrive in document order), and something precise for one task and vague for two reads as broken for the two. **The cogwheel's artwork repeats every 60°** (Font Awesome's gear has SIX teeth — measured with `scripts/measureIconSymmetry.mjs`, not assumed; it was 45° first and the third-of-a-tooth error at every rest was reported as a wobble), so it turns in 60° increments — attack, N sustain increments, release, minimum 120° — and the decision to continue is taken only at an increment's end, which is what lets it come to rest looking like itself rather than jammed mid-tooth. Phase durations are SOLVED from the angle (each curve's area is measured and the duration that makes it travel exactly one step is used), so the reader's ramp/shape/speed sliders change how the turn feels and never where it stops. The travel curve is a precomputed monotonic table: integrating per frame with one sample count while normalising by another made the wheel run backwards by five thousandths of a degree.
- [src/shared/holdTiming.ts](src/shared/holdTiming.ts) + [src/shared/cursorHoldFeedback.ts](src/shared/cursorHoldFeedback.ts) — **how long a press-and-hold lasts, and what the cursor says about it.** There are exactly TWO thresholds, and a third would mean a third kind of gesture, which there isn't: `HOLD_CONFIRM_MS` ("I meant this one, not the one next to it" — arming a purge, splitting a chapter pill, snapping a scrollbar instead of travelling, copying a colour, raising the escape ring) and `HOLD_COMMIT_MS` ("I know this is not undoable" — pinning, branching, merging, purging a song). Nine independently-chosen numbers (200, 200, 250, 250, 300, 500, 550, 700, 1000) preceded them; two controls that mean the same kind of thing should not feel different.

  A hold has two things worth saying and no natural way to say either — nothing marks that a gesture is under way, and it fires **while the button is still down**, so nothing clicks or releases and what it did may be off-screen. The cursor is the one surface every hold shares, so it carries both: the **halo swells** while the hold runs, and a **twitch** — one brief excursion of the orbit AGAINST whatever the press is doing to it — fires the instant it completes. One module and one `end(completed)` flag, because they resolve together: a completed hold does both, an abandoned one only releases the halo, and "abandoned but twitched anyway" should not be expressible. `armHold` is the only timer these gestures use, so all of it is wired in ONE place and a new hold gesture is legible without its author knowing this exists (the one rAF-driven hold, `editor/useHoldToBranch.ts`, keeps the same invariant itself and says why). **Begin and end are paired exactly once by a `settled` latch**, not by trusting callers: several sites cancel unconditionally on release, `scrollTrackHold` from inside its own completion, and a second end would retract a swell belonging to a hold still running underneath. Nested holds are COUNTED (the temp tab arms a left pin-hold and a right unpin-hold on one press) and the shortest live threshold owns the timing, since it resolves first.

  **Polarity is never passed in**: the overlay reads the live click axis and reverses it, because "a left press contracts" is a fact about the cursor, not about the gesture — a caller that names its own polarity is a caller that can get it wrong. An axis of exactly 0 (a key hold, nothing pressed) is nothing to reverse, so the twitch is a no-op by construction.

  The maths is in `editor/CursorClickCurve.ts`, all of it the user's own ramp and shape, and both effects reach `1 + max impact` so they read as one vocabulary. **The twitch** runs at the click response's own duration — it was half, and the halving read as clipped rather than sharp, so it was dropped by feel; the seam stays because that is where the decision lives — and its apex is exactly `held × (1 + i)` expanding or `held ÷ (1 + i)` contracting — measured from where the hold left the orbit, not from the base radius, which is what lets it compose with a press still sustaining underneath and finish at exactly 1 with nothing to put back. **The halo's swell** is timed off the HOLD, not the speed slider: the curve is stretched by `1 / skew` so its apex lands exactly on the threshold, which is what makes full extension mean "now" and a partial swell mean "not yet"; it then returns on the ordinary click-speed release, from wherever it actually got to — so an abandoned hold is a completed one caught early rather than a second animation. The bell is asymptotic rather than zero-ended (~9.8% of its peak at both ends), so both channels subtract their own floor; without it a discarded excursion leaves a tenth of itself standing and pops. Verified live: a right press widened the orbit 21→29px and the twitch pulled it to 19 at the apex; the halo went 8px → 9px at 120ms of a 250ms hold → 13px (base × 1.7, max impact 0.7) exactly at the threshold → back to 8px, and an abandoned hold released from 9px rather than from 13.

- **State persistence** has two independent, equally load-bearing halves — a bug in either one silently reverts a setting on restart, and each has actually shipped that way at least once:
  - *Renderer side* (`src/App.tsx`): any immediate (non-debounced) write to the persisted app-state menu MUST go through `persistMenuStateNow` — never hand-roll `buildMenuStateSnapshot` + `saveAppState` directly, and never call `persistMenuStateNow` itself from a handler declared earlier in the file without going through `persistMenuStateNowRef` (TDZ forbids depending on it directly; a plain dependency array silently pins the call to a stale, pre-persistence-ready closure instead — see that ref's own doc comment for how this was found live). Hand-rolling the direct pattern, or triggering two independent immediate persists in the same synchronous handler (see `persistMenuStateOnce`'s `extraOverrides` param), silently reverted settings on restart — confirmed as the actual cause at least five separate times across double-size mode, sidebar visibility, the options-menu auto-show-sidebar path, and review-gutter visibility.
  - *Main-process side* (`electron/stateService.ts`): every field on `PersistedMenuState` (`src/shared/appState.ts`) needs a matching line in `sanitizeMenu` — it's a hand-maintained allowlist both `saveAppState` and `loadAppState` route every payload through, and a field missing from it is silently dropped on every real read/write, no matter how correct the renderer-side code is. `isDoubleSizeMode` shipped an entire release this way. **The browser-mode mock (`src/dev/installBrowserMockBridges.ts`) does not catch this class of bug** — it clones state verbatim and never calls `sanitizeMenu` at all, so a fix verified only against `dev:browser` can look completely correct and still be broken in the real app. (The mock now seeds a stand-in User Guide family — the same fixed ids, sealed and timeless, one chapter, placeholder prose — plus one ordinary note, so guide behaviour can be exercised there at all. It is the SHAPE only: anything that reads the guide's real text still needs the real app.) Verify persistence changes against `electron/stateService.ts` directly (see `electron/stateService.test.ts` for the pattern: a temp-dir `StateService`, a *fresh second instance* reading back what the first wrote, simulating a real restart — not the same instance's own cache) or a real Electron build, not just the browser mock.

  If you're adding a new instant menu-state toggle or a new persisted field, both halves are required, not optional groundwork to skip.

## Diagnostic traces (opt-in, cost nothing when off)
These `localStorage` flags turn on traces built for defects that only reproduce in a real session. Each attaches nothing when unset; set the flag, reproduce, read, unset.
- `thockdown:debug-cage-state` — one line per keypress from the edit view's caret-cage reconcile: where the caret sat, what CM6 moved on its own (its height-map revision compensation), the height change, the target, what was written, and scroll/height/text rows separately. **Text movement is scroll movement minus height change** — reading the scroll number alone will mislead you, and did for most of a session. Also buffered on `window.__cageTrace` (last 400), because a console filter or another flag's flood will otherwise hide the one line you need: `copy(window.__cageTrace.join('\n'))`.
- `thockdown:debug-preview-window` — **the whole windowed-scroll story in one buffer** (`editor/scrollTrace.ts`): the block window (`win`), the travel engine (`journey`), and the long-journey curtain (`bridge`). They share a buffer because they are three views of one event — a travel plans a journey, the journey clamps against whatever the mounted window can hold, the window re-anchors under the curtain, and the curtain covers the moment it does. A defect in one presents as a symptom of the others, so separate buffers would mean reordering the halves by eye, which is exactly the reconstruction that hides ordering bugs. Every line carries `scrollTop` where it has one, because a movement of the WINDOW and a movement of the READER look identical from outside and are not the same event.
  - `win` (`usePreviewWindow.tsx`) — each adjustment pass with its geometry, each window move (marked `FRONT` when the leading edge moved, the only kind that has to compensate scroll), each carry of the reader across such a move, each landing, and the two branches that used to be silent: `defer` (a journey owns the scroller, so the window will not move for that journey's whole duration — the first thing to suspect when a travel across a large note stalls) and `hold` (the pass ran and declined to move, with the `headroom` the mounted window can still absorb; headroom near 0 plus a hold is the reader against a boundary the window is refusing to open).
  - `journey` (`NonQuantizedSmoothScroll.ts`) — the plan, with `asked` against `reachable`, which differ precisely when the destination is not in the scroller's space; every `PINNED` frame where the engine asked for a position the scroller could not give, counted rather than logged per frame (one is rounding, forty is a wall — this is what "the scroll did not arrive" looks like from the inside); the `CUT` and what `onBridgeCut` handed back; and the landing, marked `SHORT` when the target was outside the scroller.
  - `bridge` (`scrollBridge.ts`) — why `begin` declined, when it does (no host box, no style, no tile), and the arithmetic that decides whether the curtain can read as text at all: pixels per frame, **viewports per frame**, and **tiles per frame**. More than a viewport per frame and the reader sees disjoint slices rather than motion; near a half-multiple of the tile period those slices alternate between two phases and it reads as a flicker rather than as text — the wagon-wheel case `BRIDGE_TILE_LINES` was chosen to avoid, which the trace names in words when it detects it. Also flags a curtain that was raised and never advanced.
  - The flag is read **live**, not latched at first use, so it can be switched on from the console with the symptom still on screen — these defects are intermittent and a reload loses them. Buffered on `window.__previewWindowTrace` (last 400): `copy(window.__previewWindowTrace.join('\n'))`.
- `thockdown:debug-wheel` (`editor/wheelTrace.ts`, written by `CM6Editor.tsx`'s `handleWheel` and the render view's in `usePreviewScrollbar.ts` — one shared buffer, because a gesture can cross panes; the render view's lines all start `preview`) — one line per wheel event in the edit view: the raw `deltaY`/`deltaMode`, the learned notch size and pixel remainder (`editor/wheelNotch.ts`), `scrollTop` before/after/one-frame-later, and the **top visible line number** before and after, plus every silent decline. Start here for any "scrolling feels wrong" report: the first question is what the device is actually sending, and a wheel that moves `scrollTop` without moving the text is indistinguishable from one that does until the line number is on the line. Buffered on `window.__wheelTrace` (last 400). The render view's lines cover the same ground for spin-to-keep-scrolling there: every nudge with the pixels it is worth, every swallowed spin tail, and why each coast ended.
- `thockdown:debug-preview-settle` (`src/editorSection/previewSettleTrace.ts`) — why the render view was revealed after a note load, and what moved afterwards. A visible settle in render view does NOT by itself mean the settle gate is too short: it means either that the gate revealed at a real fixed point and something moved AFTER it, or that it gave up on its safety bound/timer, or that it never engaged at all. Those are indistinguishable from outside and need different fixes, so every reveal names its own reason. The post-reveal watcher then follows the geometry for 2.5s and reports **`scrollTop`, `scrollHeight` and the block container's height separately, plus `textShift`** — the on-screen position of one latched block, which is the only number that says what the READER saw: a `scrollHeight` jump with `textShift` at 0 is the scrollbar thumb alone, while a non-zero `textShift` is the reflow being reported. (Same lesson as the cage trace's: text movement is scroll movement minus height change.) A latched block merely UNMOUNTING is not counted as movement — counting it reported a phantom reflow on a capture where all three geometry numbers were flat at zero delta, which is the opposite of what the watcher is for. Buffered on `window.__previewSettleTrace` (last 400): `copy(window.__previewSettleTrace.join('\n'))`.
- `thockdown:debug-frame-cost` (`src/editorSection/previewFrameCostTrace.ts`) — what scrolling the render view costs, per frame: one line per scroll run carrying `frames`, `median`, `p95`, `max` and a dropped-frame count. Start here for any "scrolling feels wrong" report, because it answers in the units the complaint is made in. Reported as a distribution and never as a mean, deliberately: scrolling that is smooth except for a hitch every twenty frames reads as broken, and a mean erases exactly that — the p95 and the dropped count are what a reader feels, the median only says whether the baseline is healthy. Runs under ten frames are discarded as nudges, and scrolls fired while the settle gate is holding are ignored (those are the restore's, not the reader's). **Useless in the Claude Code browser pane**, which never composites and never fires rAF, so it has to be read in the real app. Buffered on `window.__previewFrameCostTrace` (last 200). Built to settle whether the continuous pane could stop virtualizing — it could, and it has — and kept because "is scrolling slow now" keeps coming back.
- `thockdown:debug-focus` (`src/dev/focusDiagnostics.ts`) — every mousedown in the capture phase with `defaultPrevented`, what holds focus one frame and one tick later, and every focusin/focusout naming both parties and their section column.
- `thockdown:debug-input-lag` — the pre-existing keystroke/scroll-sync trace. Loud; turn it OFF before reading either of the others.

## Verification rigor: match the size of the change
Two tiers, chosen by judgment, not by rote:
- **Substantial/structural work** (new features, architecture or contract changes, cross-cutting refactors, anything touching editor/scroll/performance-critical code): gold standard. Live-browser Playwright verification (not just code reading), the full existing regression-script suite, `npm test`, `tsc`/`lint`, and an A/B check (e.g. `git stash`) proving a fix's own test actually fails without it. Update the relevant living doc/JSDoc history.
- **Small, well-understood fixes and extensions** (isolated bug fixes, cosmetic tweaks, small additions with an obvious blast radius): light pipeline. Reproduce the issue, apply the minimal fix, verify the fix actually resolves it (a targeted live check beats guessing from code), done. Don't run the full regression suite or unit test suite out of habit — that cost is disproportionate to a small, isolated change and burns session budget for no added confidence.
When unsure which tier applies, ask rather than defaulting to the expensive path.

### Diagnosing a live defect (learned the hard way, repeatedly)
Order of operations, cheapest and most decisive first:
1. **Get the state difference, not the theory.** When the same code path works sometimes, the fastest question to the user is "what is the minimal difference between a run that works and one that doesn't". "Works if I reload on X, fails if I reload on Y" localizes a bug faster than any amount of code reading, and only the user can produce it.
2. **Diff the two runs.** With a working path and a failing path in hand, log both and compare. If the logs are identical through the suspect code (they were here), the fault is in runtime state or ordering, not in the branch you were about to rewrite.
3. **Take one runtime measurement that splits the hypothesis space.** Here, three numbers -- the computed target, what the scroller could hold, and where it actually ended -- killed "miscomputed" and "clamped" in a single read and left only "discarded". That is worth more than another speculative patch.
4. **Instrument decision points, including the silent ones.** Log what was computed, which branch ran, and what each early return declined to do. Every unlogged `return` in a correction path is a place the bug can hide.
5. **Only then change code.**

**The browser mock cannot measure anything proportional to note size.** `installBrowserMockBridges.ts` serializes its whole store to `localStorage` on every write, so a multi-megabyte note under test shows up as a large `persistStore`/`setItem`/`clone` cost that does not exist in the real app (SQLite over IPC there, and not on the activation path at all) — ~177ms of a 1131ms profile on a 1953KB note, plus an unknown share of the unattributable `(program)` bucket. It scales WITH the note, so it cannot be subtracted as a constant. Read the ordering of app-level frames from `dev:browser`; take absolute numbers and native buckets from a packaged Electron build (`scripts/perf/measureLargeNoteFirstOpen.mjs`).

**Know what your instrument cannot do.** `dev:browser` in the Claude Code Browser pane does not composite, so `requestAnimationFrame` never fires there: anything rAF-scheduled (the settle gate, the anchor-jump correction, every retry loop in the editor) simply does not run, and measurements of it are meaningless rather than merely imprecise. Establish whether the path under test can even execute in the instrument *before* trusting a result from it -- and never ship a speculative fix to timing-sensitive code that the instrument cannot exercise. Shipping unverified guesses to the user's running app burns their time and can break working behavior; it did both here.

**Smoke-load after touching hook-level code.** `tsc` does not catch temporal-dead-zone ordering (a `const` ref declared after the callback that closes over it), and the symptom is a blank app, not a type error. Load the app once before handing it back.

## Docs hygiene
Point-in-time planning/migration records (phase trackers, decision ledgers, validation matrices) are not kept once their work ships — the shipped code and the docs above are the source of truth. Don't recreate that pattern; if a doc is a snapshot of a finished effort, fold anything non-obvious into the relevant living doc or TODO.md and delete it rather than archiving it.

**A SPECIFICATION IS NOT A RECORD, and this rule has already eaten one.** `docs/adventure-game-design.md` — the game's rules, authored by the user — was deleted by `5523f8f` under the paragraph above, taking six open questions with it and leaving every later session to infer the rules from the code that implements them. The test is not how finished the work is, it is **who the document answers to**: a record describes work that HAS been done and is superseded by that work shipping, while a specification says what the code OUGHT to do and is superseded only by its author. Where a spec describes something unbuilt, the doc is ahead and the code is behind — that is the document doing its job, not a snapshot going stale. **If you did not write it and it states intent rather than history, it is not yours to delete: put it in the list above instead.**
