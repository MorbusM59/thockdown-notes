# Mobile soundscape app

The desktop soundscape panel and engine, alone, as an Android app (iOS later).
The whole interface is `SoundscapeControls` from
`src/sidebar/SoundscapeOptions.tsx` plus an on/off switch and a master
volume, which the desktop keeps on the audio bar instead. Nothing here is a
copy: the panel, the engine (`src/sound/SoundscapeEngine.ts`), the worklet
(`public/soundscape-generator.js`) and the settings model
(`src/shared/soundscape*.ts`) are the desktop's own files, so a change there
reaches both.

## Look
The desktop's **Paper** light preset, fixed. It is drawn by the same code the
desktop uses (`src/shared/loadoutTheme.ts` for the variables, filter and
overlays, `src/components/ThemeLayers.tsx` for the glaze and blend layers),
inside the same frame elements, so a change to Paper reaches both. Textures
are the one part of a preset the phone does not draw: they are rendered by a
worker and cached by the desktop's main process.

## Layout
- `mobile/src/` — the web app: `MobileSoundscapeApp.tsx` (the screen),
  `preferencesStore.ts` (localStorage, through the desktop's sanitizer),
  `backgroundAudioHost.ts` (the interface to the native side).
- `mobile/android/` — the Capacitor Android project. The only hand-written
  native code is `BackgroundAudioPlugin.java` and
  `SoundscapePlaybackService.java` in `app/src/main/java/com/thockdown/soundscapes/`.
- `capacitor.config.ts` (repo root) — points Capacitor at both.

## Background playback
The sound is generated by Web Audio inside the WebView. Android freezes or
kills a background app's process, and the WebView's audio with it, unless the
app holds a foreground service. So while a soundscape is audible the web side
calls `backgroundAudioHost.start()`, which starts a mediaPlayback foreground
service with a notification and lock-screen entry (with a Stop control) and
a partial wake lock; `stop()` ends it. Both calls come from the same effect
that drives the engine, from the same `isSoundscapeAudible` rule, so the
notification and the sound cannot disagree.

iOS will need the same interface implemented with an AVAudioSession in the
playback category. Whether WKWebView keeps Web Audio running in the background
even then is unknown; if it does not, the worklet has to run natively, which
is why the DSP must stay free of DOM dependencies.

## Build
- Browser, for the interface: `npm run mobile:dev`.
- APK without Android Studio: run the **Build Android APK** workflow from the
  Actions tab and download the `thockdown-soundscapes-debug-apk` artifact.
- Locally, with the Android SDK: `npm run mobile:build`, then
  `cd mobile/android && ./gradlew assembleDebug` (or open `mobile/android` in
  Android Studio).

## The device test this spike exists for
Unverified until it has run on a real phone. On the device:
1. Start a soundscape (e.g. Thunderstorm), confirm the notification appears.
2. Lock the screen. Leave it 30 minutes. Does the sound continue without
   dropouts?
3. Switch to another app and use it for a few minutes. Still playing?
4. Press Stop in the notification: the sound stops and the in-app power
   switch shows off.
5. Repeat step 2 with battery saver on.
6. Then remove the wake lock (`SoundscapePlaybackService`) and repeat step 2.
   If playback survives without it, it stays deleted.

## Known gaps
- The panel's secondary gestures are right-click gestures on desktop
  (solo/disable a layer, export or delete a custom soundscape). Android maps a
  long press to `contextmenu`, which covers the handlers that listen for it,
  but not those that read `button === 2` on pointer events (layer solo and
  hold-to-disable). Touch needs its own declared gesture for these rather than
  an emulated right button.
- Export/import of `.tds` files is not wired: `exportSoundscapes` is a no-op
  without `window.thockdownSoundscapeFiles`. It needs a native share/save
  implementation of `SoundscapeFileApi`.
- No app icon or splash yet (Capacitor defaults).
