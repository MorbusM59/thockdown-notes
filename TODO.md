- [ ] **A first click into a non-active section marks it active without giving it working focus** (user-reproducible every time; suspected to be behind the "left/primary editor steals focus" reports, and worth fixing early because a mis-focused pane quietly corrupts any other scroll/caret diagnosis run near it). Repro: two sections, left in render view and ACTIVE having just been scrolled with the arrow keys, right in edit mode. One click on the right editor: it shows as active, but no caret appears even though its position is inside the viewport, and the arrow keys no longer move the caret -- they nudge the text up and down by a fraction of a row, clamped, as if something is scrolling rather than navigating. A SECOND click restores normal behavior.

  **Measured, user-supplied:** `document.activeElement` is `body` after the first click and `div.cm-content.editor-text.cm-lineWrapping` after the second. So focus is genuinely never applied on the first click -- this is focus application, not key handling, and the arrow-key nudge is just what arrow keys do when nothing is focused.

  **Narrowed by probe:** with BOTH sections in edit mode and focus deliberately dropped to `body` first, a single click into the inactive section focuses it correctly (`cm-focused` = 1), and the `.cm-content` node is *not* replaced across activation (tagged and compared). So it is neither generic first-click behavior nor a DOM remount. The remaining ingredient is the other section being in RENDER view, which is exactly the precondition the Playwright harness could not set up -- neither the per-section toggle button nor Escape switches a column's mode from a script, so this needs the real app or a harness that can drive mode switching.

  **A guard is in place, and it is paint, not a cure** (`EditorSection.tsx`, the `wasSectionActiveRef` effect): a section entering the active state in edit mode, with focus not already inside it, now schedules `scheduleFocusEditorInEditMode`. It closes a real gap on its own terms -- `markSectionActive` only sets `activeSectionId`, so nothing anywhere put focus in the newly active section, and activation should never be able to disagree with focus. But it is NOT verified to fix the reported defect: no harness can construct the state the defect needs, and with the guard stashed the same probe passes identically, so nothing demonstrates the guard changing behaviour. **Keep this item open.** If the symptom returns, the guard means it will look different (focus may arrive late rather than never), so re-measure before assuming anything.

  **Also worth knowing:** it stopped reproducing after an app restart, which says the trigger is accumulated session state rather than a fixed code path -- consistent with every harness, which always starts clean, failing to reproduce it.

  **Ruled out so far**, each by measurement rather than reasoning: DOM replacement (the `.cm-content` nodes are tagged and identical across activation); generic first-click behaviour (one click focuses correctly in both harnesses); a timing race against the render pane's arrow-scroll animation (clicking at 0ms, 150ms and 1500ms after the arrows all focus correctly); and the runtime itself (the real Electron app, driven with an isolated `--user-data-dir`, also focuses on the first click). So the trigger is something in a real session's state that a freshly-seeded harness does not have.

  **Instrument for it: `src/dev/focusDiagnostics.ts`.** `localStorage.setItem('thockdown:debug-focus', '1')`, reload, perform the gesture, and read the `[focus]` lines: every mousedown in the capture phase with its `defaultPrevented`, what holds focus one frame and one tick later, and every focusin/focusout with both parties and their section column. A `focusout ... to=null` names whatever is pulling focus back to `<body>`; no focusin at all after the mousedown means focus was never applied rather than applied and stolen. Costs nothing when the flag is off -- the listeners are not attached.

  `markSectionActive` (App.tsx) only calls `setActiveSectionId`; nothing focuses the newly active section's editor. `scheduleFocusEditorInEditMode` exists and is called on MODE changes (the render->edit fast path) but never on a section-activation change. A guarded self-healing fix -- on `isSectionActive` becoming true, in edit mode, with focus not already inside this section, schedule that same focus -- is the obvious candidate, but it compensates rather than cures and should not be shipped until the render-view interaction is actually understood and reproducible.

## A monster's conditional effects never reach it
`buildMonster` (`src/adventure/model/monsters.ts`) calls `resolveProfile` with
no `Situation`, so every `derivedPercentWhileHealth` and `derivedPercentOnAction`
on a monster species resolves against the default: `hurtFraction` 1 and neither
round edge. **Measured**, not inferred — a Ghoul built with its two conditional
effects and one built without them have identical `damage` and `maxHitPoints`.

Three monster species are affected today: **Ghoul** and **Lich** (`injured`
self-conditionals that can never fire) and any `healthy` one, which would fire
*always* rather than conditionally. It also blocks `subject: 'target'` content
on the monster side — a wolf pack that finishes a maimed player, which is what
the band was asked for.

The player side has no such problem: `actingProfile` (`stages/combat.ts`)
re-resolves per action with the live situation. **What would have to be true to
fix it**: a `Monster` would have to stop being a snapshot frozen at offer time
and be re-derived per action the way the player's profile is — which touches
what is persisted in the encounter's stage state, so it is its own change.
