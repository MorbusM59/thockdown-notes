- [ ] **A mode-toggle round trip does not return edit to where it was, and after a scrollbar jump it misses by a mile.** Measured on a 200k-char note (dev:browser, Playwright): a wheel scroll to 312px, toggle to preview and back, returns to 52px. A scrollbar-track click to **31590px**, same round trip, returns to **5356px** -- 26,234px short. Not a regression from the RESTORE_OFFSET_LINES sign fix: the same probe on the previous commit gave 5408px, i.e. identical behavior differing only by that fix's own 2 rows.

  The number is the tell. 5356 / 26px = 206 rows, and 206 is a *source line* number, not a row count. So render->edit is landing on the naive `landScrollTopLines(sourceAnchorLine, ...)` placement -- which is only valid when one source line is one visual row -- and the wrapping-aware correction (`resolveCorrectedScrollTopLines` -> `resolveHeightForSourceLine`) is not taking effect. `EditRestoreSnapshot`'s own doc comment describes that naive value as a rough placement the adapter is supposed to correct one frame later; on a far-down line in a wrapped document it evidently does not.

  Two candidates, both worth checking before writing code. (1) `resolveHeightForSourceLine` for a line CM6 has not rendered is an estimate off its heightmap default -- the settle loop at `useEditorSectionMount.ts:1190` already documents exactly this hazard, so the question is why it does not converge. (2) The scrollbar travel animation reports **every frame** as `origin: 'scroll'`, i.e. as a genuine user scroll (confirmed in the scroll-sync log), which bumps `userScrollInterruptTokenRef` -- and that token is precisely what makes the settle loop stand down. A scroll the app itself started should not be classified as the reader taking over.

- [ ] **A first click into a non-active section marks it active without giving it working focus** (user-reproducible every time; suspected to be behind the "left/primary editor steals focus" reports, and worth fixing early because a mis-focused pane quietly corrupts any other scroll/caret diagnosis run near it). Repro: two sections, left in render view and ACTIVE having just been scrolled with the arrow keys, right in edit mode. One click on the right editor: it shows as active, but no caret appears even though its position is inside the viewport, and the arrow keys no longer move the caret -- they nudge the text up and down by a fraction of a row, clamped, as if something is scrolling rather than navigating. A SECOND click restores normal behavior.

  Not yet root-caused. The browser-mock harness could not reproduce it and could not even drive the precondition -- neither the per-section toggle button nor Escape would put a column into render view from Playwright -- so the reliable instrument here is the manual repro, not a script. The cheap decisive measurement is `document.activeElement` in DevTools immediately after the FIRST click: if it is not the right pane's `.cm-content`, this is a focus-application bug (`scheduleFocusEditorInEditMode` not running, or running against the wrong section); if it IS focused, then the arrow keys are being consumed by a scroll handler before CM6 sees them, and the nudge-by-a-fraction-of-a-row look points at the row-grid/cage scroll path rather than at caret movement.
